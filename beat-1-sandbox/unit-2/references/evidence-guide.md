## Environment

<!-- Where the environment record lives, and what a sufficient one
looks like against the issue's stated target. -->

**Where it lives:**

In the eval bundle - 
"Issue", "Candidate claim comment" or "Candidate repro report"

On Github.com - 
the claim comment and repro check in the Issue thread as text, screenshot, or artifacts attached in attachment zone directly below comment box or repo's docs against the environment listed in the issue

**What good looks like:**
The version and OS names match what the issue targets, or the difference is called out.


## Steps

<!-- Where the reproduction steps live, and what makes them followable
by a stranger, starting state to trigger. -->

**Where it lives:**
In the eval bundle - 
"Candidate repro report"

On Github.com - 
the claim comment and repro check in the Issue thread as text, screenshot, or artifacts attached in attachment zone directly below comment box or repo's docs

**What good looks like:** 
1. Provides verificaiton of the start state
2. Each step logically follows each other, as in the resulting information in the previous step should be the logical entry point for the next step. 
3. Exact names, files versions, paths, input, etc.  that the user interact with are mentioned


## Behavior shown

<!-- Where the artifacts live (output excerpts, logs, screenshots),
and what it means for an artifact to show the issue's behavior rather
than an adjacent one. -->

**Where it lives:**
In the eval bundle - 
"Candidate claim comment" or "Candidate repro report"

On Github.com - 
the claim comment and repro check in the Issue thread as text, screenshot, or artifacts attached in attachment zone directly below comment box or repo's docs against behavior listed in issue

**What good looks like:** 
The reproduced outcome matches the exact error name and/or output value that the issue body mentions. 

## Honesty

<!-- Where claims and their backing meet: how to tell a report that
says exactly what happened (including an honest cannot-reproduce) from
one that claims more than its evidence shows. -->

**Where it lives:**
In the eval bundle - 
"Candidate claim comment" or "Candidate repro report"

On Github.com - 
the claim comment in the Issue thread as text or screenshot, artifacts attached in attachment zone directly below comment box or repo's docs

**What good looks like:**
All claims the contributor makes should have evidence in the comment. For example, the claim that the the bug has been correctly reprouced can only be made with the evidence of that error.
